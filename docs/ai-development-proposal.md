# 📋 المقترح المتكامل لتطوير الذكاء الاصطناعي الداخلي في Septimus OS

> **نطاق التحليل:** قراءة كاملة لأكواد `ai-sidecar/` و `ai-agents/` وخدمات الذكاء في `backend-core/services/` ومعالجات `backend-core/handlers/` ومكوّنات الذكاء في الواجهة الأمامية، إضافة إلى كل ملفات التوثيق (`docs/`, `README.md`, specs).
>
> **القاعدة الحاكمة للمقترح:** لا حاجة لمزيد من ميزات الذكاء الآن — الميزات الموجودة أكثر من البنية التي تحملها. الاستثمار الأعلى عائدًا هو التوحيد ثم الذاكرة الموحدة، وبعدها تُبنى كل ميزة جديدة في أيام بدل أسابيع.

---

## 1. خريطة الوضع الحالي (ما هو مبني فعلًا)

طبقة الذكاء الحالية ليست طبقة واحدة بل **ثلاث طبقات متوازية متداخلة** بُنيت في مراحل مختلفة:

| الطبقة | الملفات الرئيسية | الحالة | ماذا تفعل |
|---|---|---|---|
| **ai-sidecar** | `ai-sidecar/main.py` (658 سطر) | ✅ نشطة في Docker | مستمع NATS + وكلاء ReAct بأدوات حقيقية (بحث معرفي، إنشاء مهام وصفقات، سياسات HR)، RAG على pgvector، تقدير Story Points، ردود الدردشة الآلية، الصوت (Whisper STT + TTS)، تقييم العملاء المحتملين (Lead Scoring)، تخطيط السبرنت، توليد المهام الفرعية |
| **ai-agents** | `ai-agents/agents/orchestrator.py`, `rag_engine.py`, `rag_query.py`, `events/nats_listener.py` | ⚠️ غير مفعّلة في docker-compose (تشغيل يدوي عبر Makefile) | فريق وكلاء LangGraph ثلاثي (محلل ← استراتيجي ← مراجع)، RAG على **ChromaDB محلي** بنموذج MiniLM، مستمع NATS JetStream دائم (durable consumers)، نسخ مكررة من plan-sprint و generate-subtasks |
| **طبقة Go الأصلية** | `backend-core/services/embeddings.go`, `services/agents/{llm_provider,orchestrator,runners}.go` | ⚠️ نصف حقيقية | توليد Embeddings عبر Gemini `text-embedding-004` وتخزينها في pgvector (`document_embeddings`)، تجريد مزوّدي LLM (OpenAI/Gemini)، وكلاء CRM/Task/Comm بآلية Kill-Switch — **عملهم الفعلي محاكاة `time.Sleep` وليس ذكاءً حقيقيًا** |

**الواجهة الأمامية جاهزة أكثر من الخلفية** — 7 مكونات ذكاء بمجموع ~1400 سطر:
`AgentChatDrawer`, `AIOrchestratorView`, `AIRecapModal`, `AiReport`, `AIAutoPlanModal`, `DeployAgentModal`, `AISettings`, إضافة إلى `AgentOrchestrator`.

### نقاط القوة الحقيقية

1. **البنية الحدثية (NATS JetStream)** — أساس ممتاز للذكاء الاستباقي: الوكيل يستمع للأحداث بدل أن يُستدعى.
2. **نمط JSONB Entity** — يعطي الوكلاء قدرة قراءة/كتابة موحّدة على كل الكيانات (مهام، صفقات، فواتير، سياسات) عبر أداة واحدة.
3. **قاعدة «بايثون لا يكتب في قاعدة البيانات أبدًا»** — قرار معماري سليم يحصر كل التعديلات في Go API ويُبقي مسار التدقيق مركزيًا.
4. **أدوات ReAct حقيقية** في `/api/v1/ai/chat` — تنفّذ فعلًا (إنشاء مهمة، إنشاء صفقة CRM، قراءة سياسات HR).
5. **دعم عربي مقصود** في الـ prompts والردود الصوتية.

## 2. الفجوات والمخاطر الجوهرية (مرتبة بالخطورة)

### 🔴 حرجة — يجب حلها قبل أي توسّع

| # | الفجوة | الموضع | الأثر |
|---|---|---|---|
| 1 | **ثلاثة أنظمة RAG متضاربة لا تتشارك المعرفة**: Go يفهرس بـ Gemini (بُعد 768) في `document_embeddings`؛ الـ sidecar يستخدم LangChain PGVector في جداول `langchain_pg_*` منفصلة؛ ai-agents يستخدم ChromaDB محلي بـ MiniLM (بُعد 384) | الطبقات الثلاث | مستند يُفهرس في مكان والوكيل يبحث في مكان آخر — **المعرفة مشتتة والإجابات ناقصة بالتصميم** |
| 2 | **تسريب بين المستأجرين**: `similarity_search(content, k=3)` يبحث في مجموعة `workspace_documents` العامة **بدون فلتر workspace_id** | `ai-sidecar/main.py` (معالج الرسائل) | أي مساحة عمل ترى مستندات غيرها — أخطر ثغرة عند التعدد |
| 3 | **معرّف workspace ثابت في الكود** (`797ec9d1-…`) كقيمة افتراضية في ~6 مواضع | sidecar + rag_handlers.go | يعمل في العرض التجريبي وينهار في الإنتاج |
| 4 | **الذاكرة الحوارية وهمية**: `MemorySaver()` جديد يُنشأ **داخل كل طلب** في `/api/v1/ai/chat` — الوكيل ينسى المحادثة بين كل رسالة ورسالة رغم وجود `thread_id` (بينما مسار workflow يستخدم `AsyncPostgresSaver` صحيحًا) | `ai-sidecar/main.py` | تجربة «مساعد بلا ذاكرة» |
| 5 | **مسارات `/internal/*` بلا مصادقة** ومفاتيح API تنتقل نصًا صريحًا عبر HTTP داخلي | backend-core + sidecar | مقبول محليًا فقط؛ غير مقبول عند أول نشر خارجي |

### 🟡 متوسطة

1. وكيل المراجعة (Reviewer) في `orchestrator.py` يوافق آليًا على كل شيء تقريبًا — «الموافقة البشرية» شكلية.
2. لا بث تدفقي (Streaming) — المستخدم ينتظر الرد كاملًا.
3. embeddings MiniLM ضعيفة بالعربية؛ ولا توجد أي حزمة تقييم (Evals) تقيس جودة الإجابات.

## 3. الرؤية المقترحة — «طبقة ذكاء Septimus الموحدة»

**الفكرة الحاكمة:** بدل ثلاث طبقات متنافسة، طبقة واحدة بأربع ركائز، تُبنى فوق ما هو موجود لا من الصفر:

```
┌─────────────────────────────────────────────────────┐
│                واجهة الذكاء الموحدة                   │
│   (دردشة + أوامر / + بطاقات اقتراح + مركز موافقات)    │
├─────────────┬─────────────┬─────────────┬───────────┤
│  ① العقل     │  ② الذاكرة   │  ③ الأيدي    │ ④ الضمير  │
│  Router +   │  RAG موحّد   │  أدوات Go    │ حوكمة +   │
│  وكلاء       │  + ذاكرة     │  API Tools  │ تقييم +   │
│  متخصصون    │  حوارية      │  + Workflows│ مراقبة    │
└─────────────┴─────────────┴─────────────┴───────────┘
              فوق NATS JetStream (كما هي)
```

### الركيزة ① — العقل: بوابة نماذج + فريق وكلاء متخصص

- **بوابة LLM واحدة (Model Gateway)** داخل الخدمة الموحدة: طبقة تجريد تختار النموذج حسب المهمة —
  - نموذج سريع رخيص: التصنيف والتقدير (story points، lead scoring، فرز الرسائل).
  - نموذج قوي: التحليل والصياغة والتقارير.
  - دعم Anthropic و OpenAI و Gemini و **Ollama** (للنشر المحلي الحساس — ميزة بيع قوية في المنطقة).
  - الإعدادات من شاشة `AISettings` الموجودة أصلًا.
- **وكلاء متخصصون بأدوار واضحة** (تطوير للقائمة الحالية hr/crm/finance/supervisor):
  - **وكيل مشرف (Supervisor)** يوجّه الطلب للوكيل المختص — نمط LangGraph Supervisor بدل if/else الحالي.
  - كل وكيل له: prompt نظامي + مجموعة أدوات محددة + **صلاحيات RBAC خاصة به** (وكيل HR لا يرى بيانات المالية) — تُبنى فوق نظام الصلاحيات المنجز في Phase 1.
- **ذاكرة حوارية حقيقية**: `PostgresSaver` موحّد لكل المحادثات، مع `thread_id` مشتق من (المستخدم + القناة).

### الركيزة ② — الذاكرة: RAG موحّد متعدد المستأجرين

- **مخزن متجهات واحد**: pgvector فقط (القرار الموثق أصلًا في `architecture.md`)، بجدول موحّد يحمل `workspace_id` **إلزاميًا** وفلترة صارمة في كل استعلام. يُتقاعد ChromaDB نهائيًا ويُدمج مسارا الفهرسة (Go و Python) في مسار واحد.
- **فهرسة كل شيء، ليس المستندات فقط**: المهام، الرسائل المهمة، الصفقات، سياسات HR، الفواتير — كلها entities في JSONB، أي أن «ذاكرة الشركة» تتغذى آليًا من كل حدث `entity.created` عبر NATS (البنية جاهزة، ينقصها المستهلك الموحّد).
- **استرجاع هجين**: بحث دلالي + BM25 نصي (Postgres FTS مجاني) + إعادة ترتيب (Rerank) — يرفع الدقة بالعربية خصوصًا، مع embeddings حديثة متعددة اللغات بدل MiniLM.
- **ذاكرة طويلة المدى للوكلاء**: جدول «حقائق متعلَّمة» (تفضيلات المستخدم، قرارات سابقة، أنماط العمل) يستشيره الوكيل قبل كل إجابة — هذا ما يحوّل المساعد من «أداة» إلى «زميل يعرف الشركة».

### الركيزة ③ — الأيدي: أدوات حقيقية وأتمتة استباقية

- **كتالوج أدوات موحّد مولّد من Go API**: بدل تعريف الأدوات يدويًا داخل `main.py`، يُعرَّف كل endpoint قابل للاستخدام كأداة (بمواصفة OpenAPI/JSON Schema) ويُحمَّل ديناميكيًا — إضافة موديول جديد = حصول الوكلاء على أدواته تلقائيًا.
- **إحياء وكلاء Go الصوريين**: `runners.go` الحالية (CRM/Task/Comm) تحاكي العمل بـ sleep — تُحوَّل إلى موجّهات تدفع المهمة فعليًا للخدمة الموحدة وتسجّل النتيجة في `AgentCollaborationLog` (فتصبح شاشة `AgentOrchestrator` حقيقية لا عرضًا).
- **دمج الذكاء في محرك الـ Workflows**: عقدة "AI Node" في باني React Flow — مثال: «إذا وصلت رسالة عميل ← حلّل النبرة ← إن كانت شكوى، أنشئ تذكرة Zendesk وصِغ ردًا» — يستفيد من التكاملات المنجزة (WhatsApp، Zendesk، Odoo، Google Sheets).
- **الذكاء الاستباقي** (أعلى قيمة تجارية):
  - تقرير صباحي يومي لكل مدير: ما تغيّر، ما تعثّر، ما يستحق الانتباه.
  - تنبيه انحراف السبرنت قبل نهايته (velocity vs. remaining).
  - تنبيه صفقات CRM الراكدة (بلا حركة > N يوم).
  - تذكير انتهاء الإقامات/التأمين الطبي في HR (موجود في spec الموديولات — الوكيل هو من يراقبه).

### الركيزة ④ — الضمير: حوكمة وتقييم ومراقبة

- **مركز موافقات (Human-in-the-Loop) حقيقي** — تصنيف الأدوات ثلاث درجات:
  1. قراءة → فورية.
  2. كتابة منخفضة الأثر → فورية مع سجل تدقيق.
  3. عالية الأثر (إرسال خارجي، مالية، حذف) → **تتطلب موافقة بشرية**.
  - endpoint‏ `ApprovePendingAction` موجود في `agent_api.go` — ينقصه الربط الفعلي وواجهة «صندوق موافقات» (بطاقة في القناة بزرّي قبول/رفض).
- **دفاع ضد حقن الأوامر (Prompt Injection)**: محتوى الرسائل والمستندات يُعامل كبيانات لا كتعليمات؛ أي إجراء عالي الأثر ناتج عن محتوى خارجي يمر بالموافقة إلزاميًا.
- **مراقبة وتكلفة**: تتبّع لكل استدعاء (نموذج، توكنات، تكلفة، زمن، الأداة المستدعاة) في جدول واحد + لوحة في الواجهة. LangSmith موجود في requirements بلا تفعيل — أو بديل مفتوح (Langfuse) للنشر الذاتي.
- **حزمة تقييم (Evals) عربية-أولًا**: 30–50 سؤال/مهمة مرجعية (أسئلة على مستندات، تقديرات، تصنيفات) تُشغَّل قبل كل تغيير نموذج أو prompt — تحمي الجودة من التدهور الصامت.

## 4. خارطة الطريق التنفيذية (5 مراحل)

### المرحلة 0 — التوحيد والتنظيف *(الأساس — أسبوع إلى أسبوعان)*

الهدف: طبقة واحدة نظيفة قبل أي ميزة جديدة.

1. دمج `ai-agents` و `ai-sidecar` في خدمة واحدة (الاحتفاظ بأفضل ما فيهما: الـ orchestrator الثلاثي + أدوات ReAct + JetStream الدائم).
2. تقاعد ChromaDB، توحيد كل الفهرسة على pgvector بجدول واحد مفلتر بـ `workspace_id`.
3. إصلاح الثغرات الحرجة: فلتر المستأجر في البحث، إزالة الـ UUID الثابت، إصلاح مشغّل `"ai" in content`، مصادقة `/internal/*`، volume مشترك صريح للملفات.
4. ترقية النماذج لجيل 2026 + استخدام Structured Output الأصلي بدل قصّ JSON.
5. تفعيل `PostgresSaver` للدردشة (تغيير شبه سطر واحد — أثره هائل).

### المرحلة 1 — الذاكرة الموحدة *(2–3 أسابيع)*

- فهرسة كل الكيانات آليًا عبر مستهلك NATS موحّد.
- استرجاع هجين (دلالي + BM25 + rerank).
- embeddings متعددة اللغات حديثة.
- ذاكرة الحقائق المتعلَّمة.
- ترقية Doc Chat الحالي على الأساس الجديد.

### المرحلة 2 — فريق الوكلاء والموافقات *(3–4 أسابيع)*

- نمط Supervisor للتوجيه.
- كتالوج الأدوات الديناميكي من Go API.
- RBAC للوكلاء.
- مركز الموافقات (HITL) كاملًا.
- إحياء runners في Go.
- بث تدفقي للردود عبر Centrifugo (موجود أصلًا للدردشة).

### المرحلة 3 — الذكاء الاستباقي والأتمتة *(3–4 أسابيع)*

- عقدة AI في Workflow Builder.
- التقارير الصباحية والمراقبات الاستباقية (CRM/HR/المالية/PM).
- OCR الإيصالات (موجود في spec المالية).
- ربط التكاملات الخارجية كأدوات وكلاء.

### المرحلة 4 — الجودة والتشغيل *(مستمرة)*

- لوحة التكلفة والمراقبة.
- حزمة Evals العربية واختبارات انحدار للـ prompts.
- خيار Ollama للنشر المحلي الكامل.

## 6. مؤشرات النجاح (KPIs)

- دقة إجابات RAG على حزمة التقييم ≥ **85%**.
- نسبة إجراءات الوكلاء المنفّذة دون تدخل ≥ **70%** مع **صفر** حوادث إجراء عالي الأثر بلا موافقة.
- زمن أول رد (streaming) < **ثانيتين**.
- تكلفة الذكاء لكل مستخدم نشط شهريًا **مقيسة ومرئية** في لوحة.
- «التقرير الصباحي» يفتحه المدير **3+ أيام أسبوعيًا** (مقياس القيمة الحقيقي).

## 7. الخلاصة التنفيذية

النظام يملك أساسًا حدثيًا ممتازًا وواجهات ذكاء جاهزة، لكن طبقة الذكاء الخلفية **مثلثة الرأس ومشتتة المعرفة وبلا ذاكرة ولا حوكمة ولا مراقبة**. الترتيب الصحيح:

**توحيد (المرحلة 0) ← ذاكرة موحدة (1) ← وكلاء بحوكمة (2) ← استباقية (3) ← جودة مستمرة (4)**

بعد المرحلتين 0 و1، كل ميزة ذكاء جديدة سترث الأدوات والذاكرة والحوكمة مجانًا، وتُبنى في أيام بدل أسابيع.
